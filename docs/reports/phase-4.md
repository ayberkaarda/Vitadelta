# Phase 4 report: core API

Date: 2026-11-25. Branch: `feat/phase-4-core-api`.

## 1. Completed

- Catalog read endpoints: countries, nutrients (with forms), default weights, legal contact, product search and product detail.
- Effective price resolution with stock filter, deterministic offer tie-break and price staleness.
- Recommendation query: principal resolution, anonymous trial quota with atomic reservation and refund, ranking cache keyed by catalog version, market profile, scoring call with no database connection held, truncation to the visible items for anonymous callers, paging, money presentation with one rounding.
- Pairwise comparison with product metadata, row flags and explanation parameters.
- Scoring client generated from the contract at build time; timeouts, one retry on connection errors, circuit breaker, bulkhead; degraded mode `503 scoring_unavailable` with cache hits still served.
- Admin import pipeline: products JSON and offers CSV as asynchronous jobs with schema and semantic validation, all-or-nothing writes, row errors with codes, job status endpoint.
- Data model additions decided by the owner: form registry table with database-enforced form membership, stored upper-limit citation notes (migration V5).
- OpenAPI document served at runtime and compared with the contract by a test.
- Adversarial suite extended to catalog, imports and recommendations (131 tests in total).

Defects found by the adversarial suite and by an independent review; each has a regression test:

| Finding | Fix |
|---|---|
| A number with an extreme exponent exhausted memory while the cache key was built; the quota was not refunded on that path | request numbers are bounded (12 integer digits, 9 decimals, `out_of_range`); the refund runs for every outcome other than success |
| Text from a scoring rejection was copied into the public response | only allow-listed codes and translated fields are forwarded; messages are generated by the API |
| A timeout while reading the scoring response body answered 500 and was not counted by the breaker | answered 503 and counted |
| Container and firewall rejections lacked the API headers and problem body | problem bodies and headers on every rejection |
| A multipart file name with a NUL byte caused a server error | answered 422 |
| The served OpenAPI document exposed internal class names | contract schema names only |
| The country catalog was loaded without bounds | ceiling per country, batched id lookups, cache bounded by ranked items, at most 16 concurrent scoring calls |
| Import parsing had no record, field or error limits | limits with the job errors `too_many_records`, `field_too_long`, `too_many_errors` |
| Nanosecond timestamps made an identical re-import look changed | timestamps are truncated to database precision |
| Retailer tie-break used UTF-16 order | binary UTF-8 order |
| Parser messages were stored in import errors | fixed messages with a sanitised location |

Not changed, by specification: the 120 per minute limit on comparison and product reads applies to anonymous callers only; price staleness inside a cached ranking is bounded by the 10-minute cache lifetime; import-job recovery assumes the single API instance of ADR-0011.

## 4. Deviations and assumptions

- Migration V5 was added before V3 and V4 (reserved for notifications and FX); Flyway runs with out-of-order enabled and checksum validation on (ADR-0013).
- Existing upper-limit rows get an empty note in the migration and the real citation from the seed loader.
- Imports are asynchronous jobs on a bounded executor (one worker, queue of four) under an advisory lock; an import that changes no row does not bump the catalog version, while a seed run always bumps once.
- Every product item carries a `provenance` object (synthetic flag, source, label id, snapshot date), following the real-label-data decision.
- A comparison with a product that has no usable price under the stock filter is rejected with 422 (`no_offer` or `no_stock`).
- The anonymous quota is consumed only by a successful response; every failure after the reservation refunds it.
- A country above 5000 products or a saturated scoring bulkhead answers `503 scoring_unavailable`.
- Product listing and detail do not call the scoring service and carry only the flags the API computes itself.
- `excluded.noStock` counts products with offers but none in stock; `excluded.noOffer` counts products without any offer, as the contract defines.
- The OpenAPI document is public at `/api/v1/openapi.json`.
- The API image is built with the contracts folder as an additional build context.
- Until the FX module exists, another display currency returns native money with `fx.status = UNAVAILABLE`; `saved` and `alerts` on products are always false and empty.

Accepted data deviations from Phase 1 (owner decision): the EFSA fluoride upper limit is not seeded, the IOM chloride upper limit is 3600 mg, presence floors are empty.

## 8. Branch, commits and contract changes

- Branch `feat/phase-4-core-api`; small Conventional Commits, one logical change each.
- Contract changes in `contracts/public-api.openapi.yaml` and `contracts/schemas/offers-csv.columns.md`:
  - offers CSV: file-level codes `invalid_csv`, `invalid_encoding`, `invalid_header`; import limits and the job error codes `too_many_records`, `field_too_long`, `too_many_errors`; summary keys in camelCase;
  - imports: asynchronous `202` with `Location`, all-or-nothing, optional `code` on job errors, `415` and `422` for unreadable uploads;
  - comparison: `same_product`, `no_offer`, `no_stock` (422);
  - query: `mRef` null for small markets, `429` for anonymous identity creation and per-address limits, request number precision bound (`out_of_range`), causes of `scoring_unavailable`;
  - schemas: required `provenance` on product items, `belowPresenceFloor` on breakdown rows, required `nutrientCodes` on flags, explanation parameters aligned with the scoring contract, optional `forms` on nutrients;
  - examples recomputed from the scoring service output; container-level rejections documented as 400 problems.
  All are additive or describe implemented behaviour; no released client exists yet.
